# 功能设计合理性判断：方法论 + Skill 表单竞品分析（2026-08-01）

> 承接《design-review-skill-form-modal-2026-08-01.md》的代码级审查。本文回答三个方法论问题：
> 1. 判断一个功能需要设计什么内容、哪些合理哪些不合理，怎么描述
> 2. 判断标准怎么定、是否需要参照对象
> 3. 用真实竞品分析落地「新建 Skill 表单」的逐字段判定

---

## 一、功能该描述什么（5 要素模板）

每个候选功能写成一段话，含 5 个要素：

| 要素 | 内容 |
|------|------|
| 1. 用户 | 谁在用（角色） |
| 2. 场景 | 什么时候、在什么前提下触发 |
| 3. 目标 | 解决什么具体问题（可衡量的结果） |
| 4. 行为 | 系统要做什么（动作 + 输入输出） |
| 5. 验收标准 | 怎么算做完了（可验证的用例） |

> 例：「运营人员（用户）在新建 Agent 时（场景），想不手写配置就生成可用配置（目标），系统读取已选模型和工具后自动生成默认参数，允许编辑（行为）。用 `POST /api/agents` 带 5 个预设用例验证生成结果可运行（验收）。」

## 二、什么算合理、什么算不合理

### 合理特征

| 维度 | 合理的特征 |
|------|-----------|
| 用户价值 | 有真实痛点、有人主动要，不是「加了再说」 |
| 可验证 | 有明确验收标准，能测 |
| 有边界 | 说清了「不做什么」，能明确排除项 |
| 依赖明确 | 依赖的东西已存在或已排期 |
| 最小可行 | 有 MVP 路径，能拆阶段 |

### 不合理红旗

- **镀金功能**：没人提需求，「以后可能用得上」
- **假设未验证**：凭想象猜用户要，没做过访谈/数据
- **模糊验收**：描述全是形容词（「体验更好」「更智能」），不可测
- **范围蔓延**：从「列表页」蔓延到「权限系统」
- **无主场景**：说不清谁会第一个用、哪天用

判断三问：
1. 不做它，用户会损失什么？——答不上来就不合理
2. 验收标准能写成自动化测试吗？——不能就需要再定义
3. 拆掉一半，核心价值还在吗？——还在就是镀金

## 三、判断标准怎么定：参照对象是必须的

「合理/不合理」是相对概念，没有参照物就是空对空讨论。**几乎总是需要参照对象。**

### 4 类锚点

| 锚点类型 | 来源 | 例子 |
|---------|------|------|
| 竞品/同类 | 别的产品怎么做 | 「主流 Agent 平台都有配置校验，我们没有就是缺失」 |
| 行业基准 | 公认的 benchmark | 响应时间、任务成功率、覆盖率 |
| 自身历史 | 上一个版本/竞品旧版 | 「上版没做 X，用户反馈占比 30%」 |
| 用户原话 | 访谈/工单原话 | 「我每次要手动改 3 处」→ 标准：改 1 处 |

### 用参照物定标准

1. **先量化差距**：参照对象有 → 你差多少。如「竞品配置生成耗时 <2s，我们要 <5s」
2. **没有直接参照时**，降级用间接参照：
   - 第一性原理：从用户损失倒推（「不做校验，用户会配置错导致任务失败」→ 标准：错误率 <1%）
   - 自身现状当基准：「现状 10 步，目标 ≤3 步」
3. **没有参照也要有兜底标准**：至少满足「可写自动化测试」这一条

### 参照对象选错的风险

- **错位参照**：拿大厂成熟产品当基准去压自己的 MVP → 标准虚高
- **参照即合理**：竞品有 ≠ 你需要（镀金功能竞品也可能有）
- **单一参照**：只看竞品不看用户 → 做出「看起来合理」的功能

实操顺序：`先定锚点 → 量化差距 → 定验收标准（可测） → 标注参照来源`
规则：**标准必须能回答「凭什么这个数」**。

## 四、表单字段判定：逐字段 5 问 + 反向追踪

### 每字段 5 问

| 问题 | 不通过 = 不合理 |
|------|--------------|
| 1. 谁填？填的人手头有这信息吗 | 用户要去别处查才知道 → 信息可得性差 |
| 2. 系统消费它吗？在哪用 | 后端任何地方都不读 → 镀金字段，删 |
| 3. 必填还是选填，依据是什么 | 必填但有无默认值且业务非必需 |
| 4. 有默认值吗 | 90% 填一样的内容 → 设默认或直接隐藏 |
| 5. 和别的字段冲突/冗余吗 | 两字段存同一信息 |

### 最硬的判定法：反向追踪

```
表单字段 → 数据模型 → 消费代码点
```

- 提交后 grep 该字段的使用点，**没有任何代码读它 → 删掉**
- 只被后端内部消费（`created_at`、`internal_status`）→ 是**内部字段**，不该出现在用户表单里
- 唯一例外：纯记录性信息（备注）也允许，但要能说出用途

### 表单级不合理信号

- **字段数超认知负荷**：一屏 >7 个字段，无分组说明没想清楚优先级
- **必填全选**：每个都标 `*` = 每个都让用户掏信息
- **技术字段透出**：暴露 ID、枚举内部值、毫秒时间戳
- **一次问终身问**：让用户填不常用却必填的信息

表单设计铁律：**表单不是「能收集什么」，而是「必须收集什么」**——每个字段都是对用户的索取，索取必须有回报（被消费）。

## 五、竞品分析落地：新建 Skill 表单

### 参照锚点（行业多源：3 个独立权威源）

**锚点 1：Agent Skills 规范（agentskills.io，行业标准正式规范）**（https://agentskills.io/specification）

Skill 的标准定义——SKILL.md frontmatter **只要求两个字段**：

| 字段 | 必填 | 约束 |
|------|------|------|
| `name` | Yes | 1-64 字符，**仅小写字母数字 + 连字符**，不能以 `-` 开头/结尾，不能连续 `--`，必须匹配父目录名 |
| `description` | Yes | 1-1024 字符，描述做什么 + 何时用，应含触发关键词 |
| `license` | No | 许可 |
| `compatibility` | No | 环境要求 |
| `metadata` | No | 任意键值 |
| `allowed-tools` | No | 预授权工具（实验性） |
| 正文 | — | 指令，无格式限制 |

**关键：name 有严格格式约束（lowercase + hyphens），description 必填。没有 version/category/status。** 工具是 `allowed-tools`（可选字段）而非必选列表。

**锚点 2：opencode 官方 Agent Skills 文档**（https://opencode.ai/docs/skills）

与 agentskills 规范**完全一致**的字段集：`name`（必填）、`description`（必填）、`license`/`compatibility`/`metadata`（选填）、正文 = 指令。name 校验 `^[a-z0-9]+(-[a-z0-9]+)*$`（与 agentskills 相同），description 1-1024。

**锚点 3：Anthropic 官方 skills 仓库 + 构建有效 Agent 原则**
- `anthropics/skills` 官方仓库 README：「frontmatter 只要求 `name`（lowercase, hyphens）+ `description` 两字段，正文为指令」——**规范制定者的实现与 agentskills 规范一致**
- https://www.anthropic.com/engineering/building-effective-agents：工具集是环境层面的，不内嵌在 skill 里

### 三源共性结论（高可信度）

| 结论 | 验证 |
|------|------|
| 标准字段只有 name + description + 正文 | 3/3 一致 |
| **name 是 lowercase-hyphen 格式（非任意 2-50 字符）** | agentskills + opencode 都严格约束 |
| **description 必填** | 3/3 |
| 无 version / category / status | 3/3 |
| 工具是可选（allowed-tools）或环境级 | agentskills(可选字段) + Anthropic(环境级) |

### 表单字段对照表（三源）

被评审表单（9 字段）：名称、描述、分类、状态、版本、已选工具、已选MCP、输出约束、Skill 指令。

| 表单字段 | agentskills | opencode | Anthropic | 判定 |
|---------|------------|----------|-----------|------|
| 名称 | ✅ name 必填（lowercase-hyphen） | ✅ 同左 | ✅ | **对齐但格式不符**（见下） |
| 描述 | ✅ **必填** | ✅ 必填 | ✅ | **表单做成选填——3/3 违反，明确错误** |
| Skill 指令 | ✅ 正文 | ✅ 正文 | ✅ | 对齐，合理 |
| 版本 | ❌ 无 | ❌ 无 | ❌ | **0/3，纯自加** |
| 分类 | ❌ 无 | ❌ 无 | ❌ | **0/3，自加组织层** |
| 状态 | ❌ 无 | ❌ 无 | ❌ | **0/3，系统维护值** |
| 已选工具/MCP | ⚠️ allowed-tools 可选 | ⚠️ 环境级 | ⚠️ 环境级 | 产品路线选择，需自证 |
| 输出约束 | ❌ 无 | ❌ 无 | ❌ | **0/3，注入指令即可** |

### 逐字段判定（多源修正版）

| 字段 | 判定 | 理由 |
|------|------|------|
| Skill 名称 * | ⚠️ **格式不符（升级）** | 表单允许「2-50 任意字符」，三源都要求 **lowercase-hyphen**（`^[a-z0-9]+(-[a-z0-9]+)*$`）。中文名/大写会被标准拒。消费点明确但**校验规则与行业标准脱节** |
| 描述 | ❌ **明确错误（升级）** | 3/3 源都是必填，表单做成选填——**与行业标准反着来** |
| 分类 | ✅ 合理 | 管理 UI 组织层可以有；需枚举约束（参考工具表单 T5 教训） |
| 状态 | ❌ 可疑 | 系统维护值，用户无决策权 |
| 版本 * | ❌ 可疑 | 90% 填 v1.0.0，0/3 源支持 |
| 已选工具 | ✅ 合理 | 有消费点；需明确 0 个是否允许 |
| 已选MCP | ✅ 合理 | 同上 |
| 输出约束 | ⚠️ 模糊 | 消费点存在，但选项列表不清晰 |
| Skill 指令 * | ✅ 合理 | 灵魂字段，必填正确 |

### 竞品分析的结论（多源修正版）

行业标准对「Skill 创建表单」的答案是**极简**：名称 + 描述 + 指令，三个字段就是完整的最小集（3/3 源一致）。9 个字段里 **3 个对齐标准、6 个是产品自加**。

多源参照相比单一参照（初稿只拉 opencode）的**三处判定升级**：
1. **名称格式**：初稿判定「合理，仅 2 字符下限偏紧」；多源后升级为「**格式不符**」——agentskills 和 opencode 都要求 `^[a-z0-9]+(-[a-z0-9]+)*$`（lowercase-hyphen），表单「2-50 任意字符」会被标准拒
2. **描述必填**：初稿「应改必填」→ 多源 3/3 全必填，升级为「明确错误」
3. **版本/状态/分类**：0/3 源支持，自加字段定性更硬

判断自加字段是否合理的唯一标准不变：**为什么竞品（行业标准）不做，而你要做？**

- 「描述」做成选填 → 3/3 源反着来，明确错误
- 「版本/状态」0/3 源 → 要能回答「v1.0.0 这个数谁会读、在哪读」，答不上就删
- 「分类/工具/MCP」标准放环境或可选 → 「skill 市场/管理后台」路线可以加，但这是差异化设计，要有自己的参照

> 方法论价值：竞品分析把结论**反转了一半**——没有参照前「版本」只是「可疑」，标准证明它是纯自加；「描述」只被当「选填偏低优先级」，标准证明它是必填；**多源后连「名称」都被翻出格式不符**。单一参照（初稿只拉 opencode）会漏掉「名称格式约束」这条——这正是多源的价值。

## 六、健康形态建议

被评审表单最健康形态：
- 必填只剩「名称 + 指令」；描述提升为必填
- **名称校验改为 lowercase-hyphen**（`^[a-z0-9]+(-[a-z0-9]+)*$`），对齐行业标准
- 版本给默认或自动读取，去掉必填
- 状态隐藏，系统自动维护
- 加两个分组：「基础信息」（名称/描述/分类）+「能力配置」（已选工具/MCP/输出约束）

## 第 1 步 — 确认「要不要做」

判断三问，任一答不上来就先不做：

1. **不做它，用户会损失什么？** —— 答不上来就不合理
2. **验收标准能写成自动化测试吗？** —— 不能就需要再定义
3. **拆掉一半，核心价值还在吗？** —— 还在 → 镀金功能

## 第 2 步 — 按 5 要素描述功能

```
用户 → 场景 → 目标（可衡量） → 行为（输入输出） → 验收标准（可验证用例）
```

> 例：「运营人员在新建 Agent 时（场景），想不手写配置就生成可用配置（目标），系统读取已选模型和工具后自动生成默认参数（行为）。用 POST /api/agents 带 5 个用例验证可运行（验收）。」

## 第 3 步 — 定参照锚点（必须多源）

「合理/不合理」是相对概念，必须锚定参照对象。**至少 3 个独立权威源**：

| 锚点类型 | 来源 | 例 |
|---------|------|-----|
| 协议/规范 | 行业标准定义 | MCP 规范、Agent Skills 规范 |
| 真实竞品 | 同类产品现役字段 | opencode、Dify、n8n |
| 官方仓库 | 规范制定者实现 | anthropics/skills |
| 自身历史 | 上一版本/旧功能 | 竞品旧版 |
| 用户原话 | 访谈/工单 | 「我每次要改 3 处」 |

**核心规则**：
- **判定强度 ∝ 参照数量与共识度**——多源高度一致 → 可信；单源得出的「有/无」可能把单个产品设计误当行业标准
- **参照要分层**：定义层（name/description/schema）vs 连接层（url/method/headers）vs 管理层（category/status/version）——不同字段对照不同层级
- 注意「参照即合理」陷阱：竞品有 ≠ 你需要

## 第 4 步 — 逐字段「设计合理性」深度分析

每个字段四段式：**为什么设计它 → 当前定义 → 是否合理 → 竞品对比**。

**只做「内容设计合理性」（产品层）**，不要混入工程实现质量（错误绑定、提交态、状态管理是代码层另一回事）。

## 第 5 步 — 反向追踪（最硬判定法）

```
表单字段 → 数据模型 → 消费代码点
```

- 提交后 grep 字段使用点，**无任何代码读它 → 删**
- 只被后端内部消费（created_at、内部状态）→ 不该出现在用户表单
- **反向追踪要覆盖 UI 展示层与审计层**——展示/审计也算消费，只是价值分级不同

## 第 6 步 — 双挂载点检查

同一表单组件可能有多个入口（工作站 + Agent 弹窗）。**先查所有调用方再判字段**——挂载点之间可能存在行为漂移（一处完整保存、一处静默丢字段）。

## 第 7 步 — 修复方案 review（防乱改）

写修复方案时四条铁律：

1. **删除前双向检查**：无前端收集 + 无后端消费（快照/搜索/展示）**双条件**才可删——只查「表单无收集」会漏「快照有消费」
2. **跨模块引用核实代码**：别把问题误挂到无关模块
3. **竞品约束看适用场景**：agentskills 的 name 约束只对 SKILL.md 文件目录适用，对数据库实体表单不适用——导入/新建是两种场景
4. **UI 补字段先查后端能力**：后端无存储/消费的字段，补了就是假字段

## 铁律

> **表单不是「能收集什么」，而是「必须收集什么」**——每个字段都是对用户的索取，索取必须有回报（被消费）。

## 输出物

1. 逐字段判定表（含代码证据 + 竞品对照）
2. 修复优先级（P0/P1/P2，精确到文件）
3. 优化前后对照 + 线框图
4. 修正记录（记录过程中的判断纠偏和教训）

## 实践教训（被真实审查纠偏）

| # | 我犯的错 | 纠正 |
|---|---------|------|
| 1 | 只拉一个竞品就下结论 | 多源参照：至少 3 个独立权威源 |
| 2 | 分析 MCP 时跑偏到列表表格列 | 聚焦「新建表单组件」本身（范围与参照系一致） |
| 3 | 写成工程实现批判（错误绑定等） | 聚焦「内容设计合理性」（产品层判断） |
| 4 | 方案里「MCP 并入工具」无依据 | 核实代码：MCP/工具是两条注册路径，应拆分 |
| 5 | 版本字段删除漏快照副作用 | 删除前双向检查消费点 |
| 6 | 假设 UI 补字段即可用 | 先查后端是否有存储/消费能力 |
